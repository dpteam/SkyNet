# Свои веса: от кодов int8 к обучаемым мастер-копиям

Статус: M4e. Мастер-представление готово и доказано точным. Обучение кодов
ещё не подключено — это следующий шаг, и здесь написано, что именно для него
осталось.

## Почему нельзя обучать коды напрямую

Таблица хранит целочисленный код на вес и один масштаб на строку. Шаг
обновления по коду — это ±1, что меняет вес на `scale` ≈ 0.005. Полезный шаг
SGD на два-три порядка меньше. Значит 99.9% обновлений округлятся в ноль, и
модель не сдвинется вообще — при этом loss будет выглядеть «почти не
падающим», что легко списать на learning rate.

Стандартное решение — float-мастер копия. Инвариант I1 запрещает плавающую
точку.

## Решение: Q8.24

Мастер — int32 в Q8.24. При весе 0.005 это 24 бита дробной части, то есть
разрешение около 6e-11 — на три порядка тоньше самого мелкого шага, который
имеет смысл делать. Хранимые коды становятся тем, чем они всегда были:
сжатым представлением этого мастера.

```
shadow = code * scale24                (целое умножение, без сдвига)
scale24' = max|shadow_row| / 127       (целое деление)
code' = round(shadow / scale24')
```

**Почему это точно, а не «примерно».** Если в строке есть код 127 — а он есть,
потому что из него и считался масштаб — то `max|shadow| = 127*scale24`, значит
`scale24' = scale24` без остатка, и `code' = code`. Разложение в мастер и
обратная упаковка воспроизводят те же байты. Никакого сдвига, никакого
округления, только целочисленное умножение и деление.

## Доказано на реальных весах

```
skynet shadow TINY.BIN
```

```
table      shape       scales  codes  result
emb          97x96          0      0  identical
pos         128x96          0      0  identical
L0.q         96x96          0      0  identical
L0.f1       256x96          0      0  identical
L0.f2        96x256         0      0  identical
...
L3.f2        96x256         0      0  identical

[sky] weights CRC before  1B0E71FA
[sky] weights CRC after   1B0E71FA
[sky] 0 of 368833 values differ after the round trip
[sky] round trip is exact: the masters are the weights
```

368 833 значения, ноль расхождений, CRC совпал. Проверка поэлементная, а не
по CRC: CRC говорит «что-то не то», а это говорит, какая таблица и сколько
элементов — разница между пятиминутной правкой и вечером.

Это в CI блокирующим шагом. Если точность когда-нибудь сломается, узнаем сразу,
а не после трёх эпох обучения неизвестно чего.

## Про 4 бита

`skynet shadow TINY.BIN --bits 4` тоже точен: 0 из 368 833.

Теоретически 4-битный формат не может хранить свой собственный минимум:
ниббл `-8` разворачивается в `-127`, а обратно даёт `-7`. Но наш упаковщик
никогда не выдаёт `-8` — он клампит на `-7`. То есть потеря есть в теории и
не наступает на практике, и это записано, чтобы через полгода не искать
причину.

## Память

| Что | Размер |
|---|---|
| мастер одной таблицы `f1` (256×96) | 96 КБ |
| вся модель в мастерах | 1.43 МБ |
| EMS на DOS (измерено в M1) | 15 168 КБ |

Мастера берутся **по одной таблице за раз**, буфер выделяет вызывающий. На
машине без EMS — явная деградация до текущего режима «только масштабы», как
требует I6.

## Цикл обучения кодов работает

```
build/codecheck TINY.BIN dataset.txt

  loss before 0.1127
  15100 weight elements moved
  loss after  0.0608
  ten more steps: 0.0426 0.0363 0.0336 0.0222 0.0114 0.0109 0.0106 0.0104 0.0102 0.0101
  f1 rows: 0 clamped to scale 1, 0 out of range
```

Один пример, одиннадцать шагов: loss 0.1127 → 0.0101, в 11 раз. Три
утверждения проверяются раздельно:

1. **Веса двигаются.** 15 100 элементов. Ноль означал бы, что шаг ниже
   разрешения мастера — то самое, ради чего весь этот дизайн.
2. **Loss падает** и на одном шаге, и на десяти подряд. Ошибка знака дала бы
   рост, ошибка масштаба — расхождение.
3. **Модель осталась моделью.** Каждая таблица после записи снова
   разлагается и упаковывается в себя же, и обученная строка по-прежнему
   использует весь диапазон кодов (127). Строка, которая хранит коды
   величины 3, но заявляет 127, потеряла четыре бита — и loss этого не
   покажет сотни шагов.

### Почему нельзя обучать масштаб и коды одновременно

Масштаб строки теперь **выводится** из максимума весов. Если обучать его ещё
и как свободный параметр, получаются два писателя на одно число: шаг
масштаба сдвинет его, а переупаковка тут же пересчитает из нового максимума
и затрёт. Первая версия делала оба — модель обучалась шесть эпох и не
менялась, потому что каждый шаг масштаба отменялся через микросекунду.

Значит для данной таблицы — либо коды, либо масштабы, никогда оба. В коде это
одна ветка `if`, и комментарий над ней объясняет, почему она не украшение.

### Кодам нужен шаг примерно в сто раз больше

Измерено на 34 примерах, `--codes`:

| lr | эпоха 1 | эпоха 3 | эпоха 5 |
|---|---|---|---|
| 0.005 | 0.2294 | 0.1951 | — |
| 0.01 | 0.1226 | 0.0743 | 0.0686 (6-я) |
| 0.02 | 0.0878 | 0.0487 | 0.0476 (4-я) |
| 0.04 | 0.0605 | 0.0346 | 0.0351 |
| 0.08 | 0.0415 | 0.0274 | **0.0252** |

При 0.04 на 5-й эпохе виден разворот (0.0346 → 0.0356 → 0.0351), при 0.08
пока монотонно. То есть оптимум около 0.08, и он же граница устойчивости —
дальше шаг крупнее, чем нужно этой модели.

Для сравнения, только масштабы доходят до 0.0589 за **двенадцать** эпох при
lr 0.00025. То есть коды дают тот же результат за две-три эпохи.

Причина арифметическая: `dL/dW` ≈ 4e-4, а `dL/dscale` ≈ 0.1, и мастер не
делится на 127 так, как делится код. Отсюда разница в сотни раз, и её надо
помнить, чтобы не подбирать rate заново.

Побочное наблюдение, которое стоит записать: при большом lr число
сдвинувшихся элементов **падает** (19 220 → 12 809). Это не деградация:
крупный шаг быстрее приводит строки к насыщению кодов, после чего
переупаковка перестаёт менять байты. Смотреть надо на loss, а не на счётчик;
счётчик нужен, чтобы отличить «учится» от «шаг ниже разрешения», и ноль —
единственное тревожное значение.

## Что уже готово и что осталось

Готово:

- `sk_table_write_row` — запись кодов (8 и 4 бита). Без неё таблицу нельзя
  изменить, только пересобрать файл.
- `sk_shadow_load` / `sk_shadow_store` — разложение и упаковка.
- `sk_shadow_step` — шаг `w -= lr * grad` по мастерам.
- `dL/dW_eff` — считается в `sk_tr_back`, проверен двумя способами
  (см. `docs/06-training.md`).

Готово теперь и это:

- Цикл обучения кодов: `sk_train_update` под флагом `SK_TRAIN_CODES` грузит
  мастер строки, применяет `dw_f1`/`dw_f2` с trust-регионом и упаковывает
  обратно. `tests/codecheck.c` проверяет три утверждения выше.

Осталось:

1. **Формат `SKNT.BIN`.** Свой magic, версия, CRC32C и манифест обучения:
   хеш корпуса, эпоха, lr, seed. Всё это уже есть в `sk_vault`.
3. **Конвертер `TNY2 ↔ SKNT`** с проверкой, что forward побитово тот же.
4. **Обучение с нуля** на `tools/gen_corpus.py` с оценкой на отложенном наборе.

## Порядок, который не надо менять

Формат делать **после** цикла обучения, а не до. Иначе формат придётся
переделывать, когда выяснится, что апдейту нужно ещё одно поле. А цикл
обучения нельзя делать раньше мастера — без него некуда писать.

Это и есть причина, по которой всё выше написано в таком порядке.
