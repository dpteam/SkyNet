# CI: что он реально ловит

Статус: работает. Первый прогон нашёл три бага, которые локальная сборка
на Windows найти не могла в принципе.

## Зачем это, а не «зелёная галочка»

Одна машина проверяет только одну машину. Три вещи из этого списка
физически непроверяемы локально:

1. **Другая libc.** Windows-сборка шла через `_commit`/`_chsize`, Linux —
   через `fsync`/`ftruncate`. Разница в объявлениях оказалась фатальной.
2. **Другой компилятор.** gcc, clang и tcc по-разному строги к тому, что
   C89 запрещает.
3. **32-битный ABI.** «`long` ровно 32 бита» — самое нагруженное
   допущение в коде. Проверить его можно только **запуском** 32-битного
   бинарника, а не компиляцией.

## Найденные баги

### 1. `__STRICT_ANSI__` прячет POSIX

```
src/sk_io.c:133: error: implicit declaration of function 'fileno'
src/sk_io.c:160: error: implicit declaration of function 'ftruncate'
```

Причина: `-std=c89` определяет `__STRICT_ANSI__`, и под ним glibc **не
объявляет** `fileno`, `fsync`, `ftruncate` — они не входят в ISO C.

Это не «предупреждение, которое можно отключить». Это значит, что
компилятор считает функции несуществующими и подставляет `int`-сигнатуру.
На 64-битной машине это порча указателей. На Windows баг невидим, потому
что там совсем другие функции.

Правильное лечение — попросить POSIX явно, **до любого заголовка**:

```c
#if !defined(_WIN32) && ... && !defined(MSDOS)
#  ifndef _POSIX_C_SOURCE
#    define _POSIX_C_SOURCE 200809L
#  endif
#endif
```

Не костыль: это ровно тот механизм, который стандарт предусматривает.

### 2. `-Werror` и неиспользуемая переменная

```
tests/verify.c:17: error: unused variable 'got'
```

Осталась от черновика. Без `-Werror` жила бы годами.

### 3. Контейнер, которого не существует

Первая версия DOS-джобы тянула `ghcr.io/open-watcom/open-watcom-v2:latest`.
Такого образа нет:

```
failed to resolve reference: not found
```

Заменено на снапшот-тарбол с релизов upstream. Плюс вторая ошибка в том же
джобе: `mkdir -p /opt/watcom` — у runner'а нет прав на `/opt`.

## Баг, который нашёл только 16-битный компилятор

### Сначала о том, который нашла 64-битная сборка

`sk_u32` был объявлен как `unsigned long`. На Linux x86-64 `long` — 64
бита, поэтому всё fixed-point молча работало в 64-битном диапазоне.

Почему это не вылезло раньше: тесты проверяли значения, которые
помещаются в 32 бита, поэтому 64-битная арифметика давала те же ответы.
Расхождение вылезло на первом же матвеке модели — Linux дал `265.999`
там, где Windows дал `4.771`, разница в 55 раз.

Диагностика заняла один шаг, потому что `tests/sizes.c` печатает
фактические размеры типов вместо того, чтобы им доверять:

```
Windows: sk_u32=4 sk_i32=4 sk_fix=4
Linux  : sk_u32=8 sk_i32=8 sk_fix=8   <- вот оно
```

Исправление — в `sk_types.h`: выбор между `int` и `long` по `<limits.h>`
плюс assert времени компиляции. Теперь неверный тип не собирается.

Урок общий: **нельзя писать `unsigned long` и надеяться**. Это то же
самое, что «доверять, что `char` знаковый».
Самый ценный результат всей возни с DOS. `sk_io.c` определял платформу
так:

```c
#elif defined(__TURBOC__) || defined(__BORLANDC__) || defined(MSDOS)
#  define SK_PLAT_DOS 1
```

OpenWatcom определяет `__WATCOMC__` и `__DOS__`, но **не** `MSDOS`.
Поэтому файл молча компилировал POSIX-ветку на DOS-таргете:

```
src/sk_io.c(63): Error! E1151: Parameter count does not agree with
previous definition
```

То есть вызывался `mkdir(path, 0755)` там, где DOS-овский `mkdir`
принимает один аргумент. Классический баг: собирается на всех хостах,
которые у нас есть, и падает только на настоящей цели.

Причина, почему он вообще появился — **детекция была продублирована**:
отдельный список макросов в блоке feature-test и отдельный в блоке
заголовков. Теперь один `SK_IS_DOS`, используемый дважды.

Заодно убран `<dir.h>`: он нужен Turbo C для `mkdir`, но OpenWatcom его
не поставляет и объявляет `mkdir` в `<io.h>`. `<io.h>` есть у обоих —
это и есть единственный безопасный инклюд.

## Что проверено на настоящем DOS

Не «собралось», а «запустилось». DOSBox, 16-бит, 640 КБ:

| Проверка | Результат |
|---|---|
| selftest | 37/37 |
| `sizeof(int)=2`, `sizeof(long)=4` | подтверждено на целевой машине |
| malloc 60 КБ, `chsize`, `rename` | работают |
| арена: просили 8 МБ | получили 65 280 байт, прогон продолжился |
| 20 000 простых, `--ckpt 1` | 35 чекпоинтов, STATE.A + STATE.B + WAL.LOG |
| второй процесс | `resumed at prime #20000 = 224737 (seq 55)` |
| файл, записанный DOS-программой | 25 000 строк, 0 расхождений |

### Как это чинилось

Первый запуск дал **пустой вывод**. Причина оказалась не одна:

1. **Буферизованный stdout.** Самотест существует, чтобы находить
   падения, а буфер теряет всё именно при падении — крах выглядел как
   «не запустилось». Теперь `_IONBF` и `fflush` после каждой секции:
   последняя напечатанная строка называет упавший шаг.

2. **Переполнение стека.** `sk_vault` — ~900 байт (два пути по 192,
   каталог 128, журнал, скретч), и вызывающий держит его рядом с
   `sk_arena`, `sk_clock` и тремя `sk_state`. Стек DOS по умолчанию 2 КБ,
   поэтому тест vault сносил стек и выходил молча. Линковка с
   `option stack=8192`.

Чтобы не гадать, `tests/probe_dos.c` проверяет по одной возможности на
строку. Именно он сузил проблему до стека, а не до файловых операций.

### Что было перепробовано

| Инструмент | Результат |
|---|---|
| контейнер `ghcr.io/open-watcom/...` | образа не существует |
| `dev86` / `bcc` (Debian, 122 КБ) | **отвергнут**: до-ANSI компилятор, отвергает `int main(void)` — `need ')'` на любом прототипе |
| `gcc -m16` | генерирует 16-битный код, но в 32-битном ELF; для DOS непригоден |
| OpenWatcom снапшот | работает, но загрузка нестабильна |

`dev86` был бы идеален по размеру (122 КБ против 148 МБ) и по цели
(чистый 8086), но он из 1989 года и не знает ANSI-прототипов. Записан
здесь, чтобы через полгода не пробовать снова.

### Что сделано с загрузкой

Три ошибки, каждая из которых ломала job:

1. `mkdir -p /opt/watcom` — у runner'а нет прав на `/opt`;
2. `curl` без `-f` сохранял HTML-страницу ошибки как архив;
3. **параллельные попытки писали в один файл** — получался файл длиннее
   настоящего (217 МБ против 155) и битый в середине.

Сейчас: каждая попытка пишет в свой файл, условие выхода — `xz -t`, а не
код возврата curl, и результат кешируется между прогонами.

## Как проверить локально

```bash
sh tools/wsl_ci_check.sh      # все семь шагов CI в WSL/Linux
sh tools/test_watcom.sh       # проверить путь сборки под DOS
python tools/hygiene.py -v    # только инварианты
```

`tools/wsl_ci_check.sh` появился потому, что первые два бага пришлось
искать через CI — то есть вслепую, по логам. Локальный прогон тех же
шагов означает, что следующий баг найдётся до пуша.

## Правило

Если проверка не может упасть — это не проверка. Поэтому в джобе
`hygiene` есть шаг, который скармливает чекеру намеренно плохой файл и
требует, чтобы тот **завалился**:

```bash
printf '/* t */\n#include <math.h>\nint f(void){ double x=1.0; // c\n return (int)rand()+(int)x; }\n' > src/sk_zz_probe.c
if python3 tools/hygiene.py; then
  echo "::error::hygiene.py passed on a deliberately bad file"
  exit 1
fi
```
