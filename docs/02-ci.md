# CI: что он реально ловит

Статус: работает. Первый прогон нашёл три бага, которые локальная сборка
на Windows найти не могла в принципе.

## Зачем это, а не «зелёная галочка»

Одна машина проверяет только одну машину. Три вещи из этого списка
физически непроверяемы локально:

1. **Другая libc.** Windows-сборка шла через `_commit`/`_chsize`, Linux —
   через `fsync`/`ftruncate`. Разница в объявлениях оказалась фатальной.
2. **Другой компилятор.** gcc, clang и tcc по-разному строги к тому, что
   C89 запрещает.
3. **32-битный ABI.** «`long` ровно 32 бита» — самое нагруженное
   допущение в коде. Проверить его можно только **запуском** 32-битного
   бинарника, а не компиляцией.

## Найденные баги

### 1. `__STRICT_ANSI__` прячет POSIX

```
src/sk_io.c:133: error: implicit declaration of function 'fileno'
src/sk_io.c:160: error: implicit declaration of function 'ftruncate'
```

Причина: `-std=c89` определяет `__STRICT_ANSI__`, и под ним glibc **не
объявляет** `fileno`, `fsync`, `ftruncate` — они не входят в ISO C.

Это не «предупреждение, которое можно отключить». Это значит, что
компилятор считает функции несуществующими и подставляет `int`-сигнатуру.
На 64-битной машине это порча указателей. На Windows баг невидим, потому
что там совсем другие функции.

Правильное лечение — попросить POSIX явно, **до любого заголовка**:

```c
#if !defined(_WIN32) && ... && !defined(MSDOS)
#  ifndef _POSIX_C_SOURCE
#    define _POSIX_C_SOURCE 200809L
#  endif
#endif
```

Не костыль: это ровно тот механизм, который стандарт предусматривает.

### 2. `-Werror` и неиспользуемая переменная

```
tests/verify.c:17: error: unused variable 'got'
```

Осталась от черновика. Без `-Werror` жила бы годами.

### 3. Контейнер, которого не существует

Первая версия DOS-джобы тянула `ghcr.io/open-watcom/open-watcom-v2:latest`.
Такого образа нет:

```
failed to resolve reference: not found
```

Заменено на снапшот-тарбол с релизов upstream. Плюс вторая ошибка в том же
джобе: `mkdir -p /opt/watcom` — у runner'а нет прав на `/opt`.

## Джобы

| Job | Что доказывает |
|---|---|
| `build` × 5 | gcc, clang, tcc, mingw, clang/macOS — все с `-Werror` |
| `build-32bit` | 32-битный бинарник **запускается**: selftest + краш-тест |
| `crash-test` | 15 убийств, `--durable`, восстановление после порчи слота |
| `hygiene` | I1/I2/C89 + проверка, что сам чекер умеет падать |
| `dos-build` | 16-бит OpenWatcom (best effort) |

Артефакты: `skynet-linux-x86_64`, `-clang`, `-tcc`, `-i386`,
`-windows-x86_64`, `-macos`, `-dos-16bit`.

## Почему `dos-build` — best effort

Он помечен `continue-on-error`, и это осознанно. Причины:

- тарбол 148 МБ, качается с перебоями (у меня локально три раза
  обрывался на 33–72 МБ);
- 16-битная сборка доказывает только то, что **компилируется**, а не что
  работает: арена по умолчанию просит 8 МБ, которых в реальном режиме нет.

Авторитетная проверка DOS — ручной прогон в FreeDOS под `hv86`/DOSBox.
CI здесь ловит регрессии переносимости, а не заменяет эту проверку.

## Как проверить локально

```bash
sh tools/wsl_ci_check.sh      # все семь шагов CI в WSL/Linux
sh tools/test_watcom.sh       # проверить путь сборки под DOS
python tools/hygiene.py -v    # только инварианты
```

`tools/wsl_ci_check.sh` появился потому, что первые два бага пришлось
искать через CI — то есть вслепую, по логам. Локальный прогон тех же
шагов означает, что следующий баг найдётся до пуша.

## Правило

Если проверка не может упасть — это не проверка. Поэтому в джобе
`hygiene` есть шаг, который скармливает чекеру намеренно плохой файл и
требует, чтобы тот **завалился**:

```bash
printf '/* t */\n#include <math.h>\nint f(void){ double x=1.0; // c\n return (int)rand()+(int)x; }\n' > src/sk_zz_probe.c
if python3 tools/hygiene.py; then
  echo "::error::hygiene.py passed on a deliberately bad file"
  exit 1
fi
```
