# Обучение: что проверено, что улучшено, где предел

Статус: M4c. Backward до последнего блока FFN проверен численно и сверен
с эталонным PyTorch-тренером; в апдейт подключены пять видов градиента.
Следующий шаг — attention.

## Что обучено и почему именно это

Выходная проекция — последняя операция в сети, поэтому её градиент по
масштабам строк **не требует backpropagation вообще**:

```
dL/dscale[r] = sum_t dL/dlogits[t][r] * dot[t][r]
```

Каждое число — точная производная. Это важнее широты: тренер, который
обновляет параметры приблизительными градиентами, тихо не учится, и
обычно это списывают на learning rate.

Позже тем же способом добавлен backward через последний блок
feed-forward и через обе RMS-нормировки — см. ниже.

## Градиент проверен

Единственный честный способ проверить градиент без эталонной
реализации — увидеть, что loss падает на **одном** примере:

```
epoch 1: loss 0.0912
epoch 2: loss 0.0748
epoch 3: loss 0.0625
epoch 4: loss 0.0435
epoch 5: loss 0.0369
```

Монотонно, в 2.5 раза. Если бы знак был неверным, loss рос бы; если бы
масштаб — расходился. Это `tools/train_check.sh`, и он в CI.

Плюс проверка, что при `lr = 0` ничего не меняется: это доказывает, что
измерение не загрязнено самим обучением.

## Weight tying развязан

В релизной модели таблица эмбеддингов **одновременно** является выходной
проекцией. Это экономно, но один тензор служит двум целям: обновляя его
ради предсказания следующей буквы, мы ломаем представление входных букв.

Теперь `emb` и `out` — разные таблицы. `out` инициализируется точной
копией `emb`, поэтому **инференс остаётся побитово тем же** (проверено:
тот же ответ, тот же CRC весов). Цена — 9.7 КБ.

## Что улучшается и насколько

34 примера, lr = 0.001, все пять видов градиента в апдейте:

```
epoch 1: loss 0.1930
epoch 2: loss 0.1527
epoch 3: loss 0.1240
epoch 4: loss 0.1025
epoch 5: loss 0.0870
epoch 6: loss 0.0748
```

Монотонно, в 2.6 раза. Пока в апдейте была только выходная проекция, тот
же прогон давал 0.2437 → 0.2190, то есть около −10%. Backward через
последний блок даёт в шесть раз больше на том же бюджете — что
неудивительно: до этого 256 строк `f1`, 96 строк `f2` и обе нормировки
оставались замороженными.

## Три ошибки, которые пришлось найти

**1. Измерение было нечестным.** Loss эпохи считался *во время*
обновлений: первый пример — до обновления, последний — после девятнадцати.
Такой показатель менялся от learning rate даже на первой эпохе. Теперь
после каждой эпохи делается отдельный проход без обновлений.

**2. Порядок операций в RMSProp.** `delta = lr * grad / avg` считалось как
`(lr * grad) / avg`. При `grad ≈ 5000` (Q8.24) и `lr ≈ 17` произведение
меньше одного LSB и округляется в ноль — обучение не двигалось вообще, и
выглядело как «градиент исчез». Деление должно идти первым.

**3. Дрейф масштабов.** `dL/dscale[i] = dL/dlogit[i] * dot[i]`, а `dot`
различается по строкам до 60 раз. На 97 классов одна верная строка против
96 неверных: неверные получают большие градиенты и сжимаются, верная
растёт медленно. Итог — систематическое сжатие около −10000 единиц за
эпоху (0.15% от суммы масштабов). Сжатие делает распределение площе, и
loss в конце концов растёт.

Лечение — нормализация шага по строке (RMSProp): делим обновление на
бегущую величину градиента этой строки, и зависимость от `dot` исчезает.

## Градиент проверен численно

Самый сильный вид проверки без эталонной реализации: шевельнуть масштаб на известную величину, измерить сдвиг loss и сравнить с тем, что утверждает backprop.

```
numeric  = (loss(p + e) - loss(p - e)) / (2e)
analytic = dL/dp из backward pass
```

`tests/gradcheck.c` делает это для каждой строки выходной проекции:

```
97/97 rows agree within 25%, worst relative error 19.6% at row 75
```

Эта проверка нашла **три** реальных бага, которые иначе выглядели бы как «модель плохо учится»:

**1. Нет нормировки 1/n.** Loss — среднее по позициям ответа, а градиент копился как сумма. Аналитика была ровно в n раз больше численной, и деление на 5 сразу привело их в согласие.

**2. Насыщение внутри `sk_fix_mul`.** Произведение для строки с большим dot достигает 3e11 и насыщается, а после сдвига получается ровно 128.0 — число, которое выглядит правдоподобно и полностью неверно. Сдвиг нужно делать **до** умножения.

**3. Переполнение при конвертации.** `sk_g24_from16` справляется только со значениями до 128, а градиент достигает 283. Конвертация скрывала это как правдоподобное −128.0.

Плюс один баг в самом чекере: он читал аналитику внутри цикла возмущений, а `loss_of` перезаписывает `dlogits` — то есть сравнивал градиент одного состояния с производной в другом. Давало ложные 472% на верном градиенте.

## Почему шаг в чекере подбирается, а не фиксирован

Раньше здесь было «eps = 5% от параметра». Это неверно по обе стороны:
при 0.1% численный градиент выходит ровно нулём (`ΔL = grad*2*eps*scale`
при grad ≈ 0.1 и scale ≈ 0.005 даёт 1e-5 — один LSB Q16.16), а при 25% на
строках с большим градиентом softmax уже нелинейна и численная
производная уезжает в разы.

Потолок точности задаёт **представление loss**, а не градиент. Поэтому
шаг теперь вычисляется из аналитического градиента: нужен такой `eps`,
чтобы сдвиг loss составил заданное число квант. Параметр, которому для
этого нужен шаг больше 25% собственного значения, честно помечается как
неизмеримый.

## Где предел

Обучение улучшает loss на 60%+ за шесть эпох на 34 примерах и выходит на
плато. Причина, по которой это ожидаемо: релизный `TINY.BIN` обучался
часами на ~15 млн примеров и находится в локальном оптимуме. Мы
подстраиваем **641 величину из 366 528 параметров** на трёх десятках
примеров. Это не «дообучение модели», это подкрутка громкости.

Чтобы двигать качество дальше, нужны градиенты по самим int8-весам — а
это другая точность представления, не Q8.24. По порядку дальше:
attention (q, k, v, o) — там же лежит квантованный KV-кэш, который сам
является частью графа.

## Математика backprop для attention (следующий шаг)

```
attn[h] = sum_j a[j] * vs[j] * v[j][h]
a       = softmax(s)
s[j]    = (q[h] . k[j][h]) * ks[j] / sqrt(HD)

da[j]   = dot(dattn[h], vs[j]*v[j][h])
ds[j]   = a[j] * (da[j] - sum_k a[k]*da[k])
dq[h]   = sum_j ds[j] * ks[j] * k[j][h] / sqrt(HD)
dk[j][h]= ds[j] * ks[j] * q[h] / sqrt(HD)
dv[j][h]= a[j] * vs[j] * dattn[h]
```

Тонкость, которую легко пропустить: KV-кэш **квантован** в int8 с
масштабом на позицию. Значит `vs[j]` и `ks[j]` — часть графа, а не
константы, и градиент по ним тоже существует. Пропустить это — значит
обучать не ту функцию, которая выполняется.

## Backprop через feed-forward: работает, 5 из 5 видов градиента

Backward написан через последний блок: `norm → f1 → relu → f2`, плюс
финальный norm и выходная проекция. Для этого в `sk_ctx` появилась
необязательная трассировка промежуточных активаций: указатели NULL во
время инференса, поэтому сам инференс не изменился ни на байт.

```
output projection    97/97 agree, worst 19.6%   [в апдейте]
f2 (last block)      93/96 agree, worst 1291.7%
f1 (last block)     237/256 agree, worst 14906470631.1%
final gains          93/96 agree, worst 146.0%
g2 (last block)      84/96 agree, worst 580.5%
```

Первая попытка этого же кода давала 88/97 на выходной проекции и была
откачена. Причин оказалось три, и все три — не в математике.

### Ошибка 1: два формата в одном файле

`dlogits` хранился в Q8.24, а все остальные градиенты — в Q16.16. Рабочий
код компенсировал это ручным сдвигом `>> 8`, и когда сдвиг потерялся,
произведение с `dot` стало в 256 раз меньше. В чекере это выглядело как
«регрессия с 97/97 до 88/97» — то есть как проблема округления.

Вывод: **одна конвенция на весь файл**. Q16.16 везде. Точность, которую
дал бы Q8.24, возвращается позже — в апдейте, где градиент нормируется по
своему бегущему среднему и только потом переводится в Q8.24.

### Ошибка 2: не обнулялись аккумуляторы

`sk_train_zero_grads` чистил только `g_emb` — тот аккумулятор, который был
первым. Четыре добавленных позже начинали жизнь как то, что вернул
`malloc`: арена памяти не обнуляет. Выходная проекция при этом продолжала
сходиться (её аккумулятор чистился), а всё ниже по цепочке давало
перевёрнутые знаки и ошибки порядка 10^10.

Отсюда правило: **арена не обнуляет память, и «странный градиент» может
быть просто мусором**.

### Ошибка 3: `sk_train_bytes` не считал новые буферы

Арена кончалась внутри `sk_tr_run`, forward возвращал 0, и **все**
градиенты читались как ноль. Это выглядит как «backward сломан», а не как
«нет памяти». Поэтому теперь `sk_train_open` проверяет **каждый** буфер, а
не первые пять, и `sk_train_bytes` документирован как список всего, что
аллоцируется.

## Как проверять градиент, когда loss квантован

Отдельная история — сам чекер. Три его ошибки стоили больше времени, чем
backward.

**1. Шаг нельзя брать долей от параметра.** Loss — Q16.16, квант 1.53e-5,
а RMS-norm внутри forward делает loss ступенчатой функцией с шагом
ступеньки около 1e-4. Шаг, сдвигающий loss на пару ступенек, измеряет
ступеньки. Шаг в 25% от масштаба строки — это 25% логита, и softmax там
уже нелинейна: отсюда «численный градиент в 76 раз больше
аналитического» на строках, которые при малом шаге сходились.

Теперь шаг подбирается для каждого параметра так, чтобы сдвинуть loss на
заданное число квант (по умолчанию 600), а параметр, которому для этого
нужен шаг больше 25% собственного значения, помечается как
**неизмеримый** — и не судится.

**2. Расхождение ≠ неверный градиент.** ReLU включается внутри шага, и у
loss появляется излом, где центральная разность не производная. Односторонние
наклоны слева и справа это разделяют: у гладкой функции они совпадают, на
изломе расходятся. Такие строки помечаются как **нелинейные**.

**3. Разные виды — разные единицы.** Масштабы строк — Q8.24 (2^24),
гейны — Q16.16 (2^16). Один делитель на оба вида делал возмущение гейнов
в 256 раз меньше нужного, и это читалось как ошибка градиента ровно в 256.

Итог прогона по умолчанию:

```
output projection      3/3 agree,  94 unresolved,   0 nonlinear, worst  7.3%
f2 (last block)       24/24 agree,  72 unresolved,   0 nonlinear, worst  6.0%
f1 (last block)       15/15 agree, 241 unresolved,   0 nonlinear, worst  8.2%
final gains           42/42 agree,  54 unresolved,   0 nonlinear, worst  4.3%
g2 (last block)       40/40 agree,  56 unresolved,   0 nonlinear, worst  9.5%

124/124 measurable parameters agree within 25%, worst 9.5%
```

Ни одна измеримая строка не расходится больше чем на 10%. Число
«неизмеримых» велико не потому, что градиент плохой, а потому что
Q16.16 не различает производные меньше ~1e-4 при таком loss.

## Сверка с эталонным тренером

Самый сильный аргумент: `refs/Tiny-2.1-main/training/train2.py` — тот
самый PyTorch-тренер, который произвёл `TINY.BIN`. Его autograd — эталон.
`build/dumpref.py` считает на тех же весах и той же
последовательности градиенты всех пяти видов, `build/cmpgrad2.py`
сравнивает с нашими:

```
final gains        cmp= 91  within15%= 39  median 0.995
g2 (last block)    cmp= 96  within15%= 26  median 0.918
f1 (last block)    cmp=239  within15%= 75  median 0.978
f2 (last block)    cmp= 96  within15%= 38  median 0.968
output projection  cmp= 46  within15%=  8  median 0.824
```

Медиана отношения наша/эталон близка к 1.0 по всем пяти видам — значит
формулы верны. Разброс — это шум: float-эталон не квантован, а мы
считаем в Q16.16 и с насыщением, и на малых градиентах расхождение в
несколько раз неизбежно.

Формулы, которые подтвердились:

```
dL/dhf      = out^T * dlogits             (масштабы выходной проекции)
dL/dscale[r]= dy[r] * dot[r]
dx          через RMS-norm:
  dx[j] = inv*g[j]*dy[j] - (inv^3/n)*x[j]*sum_k dy[k]*x[k]*g[k]
  dg[j] = dy[j]*x[j]*inv
f2 (D x HID): dL/dmid  = f2^T * dxff
f1 (HID x D): dL/dhn2  = f1^T * dmid, с маской relu
```

## Что Q16.16 не может: уверенно неверный ответ

Измерено на `what are the tubes that carry blood called|veins and arteries.`:
наш loss 2.066, у float-эталона 3.355.

Причина не в forward — логиты совпадают в пределах 1–3% по всем позициям.
Причина в softmax: при разнице логитов 22 вероятность целевого класса
равна e^-22 ≈ 3e-7, а мельчайшее представимое число в Q16.16 — 1.5e-5.
Всё, что ниже, становится нулём, и loss на такой позиции упирается в
потолок `-ln(1.5e-5) = 11.1` вместо 22.

Практическое следствие: если модель уверенно неверна, градиент по
конкурирующим классам **теряется**. Это не ошибка кода, а свойство
арифметики, и оно записано здесь, чтобы через полгода не искать причину
заново. Лечится либо накоплением логитов в более широком формате, либо
вычитанием максимума перед softmax в Q8.24 — оба варианта меняют
инвариант I1 (никакой плавающей точки) не в лучшую сторону, поэтому
решено жить с потолком и держать его в документации.

## Что подключено к апдейту

Все пять видов, не только выходная проекция. Три таблицы масштабов
строк идут через один `sk_upd_scale_row`, чтобы шаг, trust-регион и
RMS-нормировка не могли разойтись между ними — в первой версии они были
написаны трижды вручную, и три копии расходились в единицах.

## Как воспроизвести

```bash
python tools/build_dataset.py build/dataset.txt   # 5986 пар из фактов
sh tools/train_check.sh                           # проверка градиента
skynet train TINY.BIN build/dataset.txt --epochs 4 --lr 16777

# численный чекер всех пяти видов
cc -O2 -Isrc -o build/gradcheck tests/gradcheck.c src/*.c -lm
build/gradcheck refs/Tiny-2.1-main/dos/TINY.BIN build/dataset.txt

# сверка с эталонным тренером (нужен torch)
python build/dumpref.py refs/Tiny-2.1-main/training/tiny2.pt \
       build/dataset.txt 20 > build/ref_grad.txt
build/gradcheck refs/Tiny-2.1-main/dos/TINY.BIN build/dataset.txt \
       600 0 0.25 20 -1 -1 1 > build/our_grad.txt
python build/cmpgrad2.py build/ref_grad.txt build/our_grad.txt
```

У чекера есть аргументы для сужения измерения, когда что-то расходится:
`TARGET_LSB`, `verbose`, `CAP_FRAC`, число строк, вид параметра, номер
строки. Пример — одна конкретная строка `g2` на восьми примерах:

```bash
build/gradcheck TINY.BIN build/dataset.txt 200 1 0.25 8 2 30
```
