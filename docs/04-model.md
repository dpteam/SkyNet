# Модель: как TINY.BIN попадает в 16-битный DOS

Статус: M2, загрузчик работает и проверен. Инференс — следующий шаг.

## Задача

Веса Tiny-2.1 — 367 000 параметров, 380 КБ в файле `TINY.BIN`. Нужно
загрузить их в программу, у которой нет ни плавающей точки, ни `malloc`
на мегабайт, и которая должна давать **побитово одинаковый** результат на
8088 и на x86_64.

## Три препятствия

### 1. В файле float, в ядре запрещён float

`TINY.BIN` хранит масштаб каждой строки как 4-байтовый IEEE-754. Ядро
SkyNet не использует плавающую точку вообще (инвариант I1), потому что
результат должен быть воспроизводим на машине без FPU.

Решение — не каст и не union, а арифметика:

```
float32 = (-1)^s * 1.m * 2^(e-127)
значение * 2^16 = m * 2^(e-134)      где m — 24-битная мантисса с неявной 1
```

Один целочисленный сдвиг. Точен для всех значений, которые помещаются в
Q16.16; вне диапазона — насыщение, а не переполнение. NaN и Inf в файле
весов означают порчу, и насыщение делает это видимым, а не
неопределённым поведением.

Проверено на значениях с известным ответом: 1.0, 2.0, 0.5, −1.0, 0.0, π,
1e10 (насыщается), NaN (насыщается).

### 2. 32-битная арифметика на 16-битной машине

96-членное скалярное произведение int8-весов на Q16.16-активации требует
до 38 бит. В C89 нет переносимого 64-битного типа (`long long` запрещён
правилом C89, `long` на DOS 32 бита).

Аккумулятор — пара 32-битных слов `hi:lo` в дополнительном коде.
Сложение с переносом и расширением знака, ~10 строк. Результат
насыщается, если не влезает.

### 3. `long` — это не всегда 32 бита

Самый дорогой урок. `sk_u32` был объявлен как `unsigned long`. На Linux
x86-64 это **64 бита**, поэтому всё fixed-point молча работало в
64-битном диапазоне. Тесты проходили, потому что значения помещались.

Вылезло на первом матвеке: Linux дал `265.999`, Windows — `4.771`.
Разница в 55 раз, и никакой ошибки в коде не было — только в типе.

Теперь `sk_types.h` выбирает `int` или `long` по `<limits.h>` и
доказывает выбор assert'ом времени компиляции:

```c
typedef char sk_u32_must_be_4_bytes[(sizeof(sk_u32) == 4) ? 1 : -1];
```

Новый компилятор, который сломает допущение, падает на сборке.

## Как проверено

Три независимых способа, потому что два одинаковых неверных
реализации согласятся друг с другом:

**1. Разбор формата на Python** (`tools/check_tny2.py`), написанный по
описанию формата, а не по коду C:

```
weight bytes: 365664
crc32c of weights: 1B0E71FA
```

**2. CRC в C**, посчитанный загрузчиком при разборе файла, против CRC,
пересчитанного чтением из хранилища:

```
[sky] weights crc  load 1B0E71FA  store 1B0E71FA  MATCH
```

Совпадает с Python — значит и формат, и путь хранения верны.

**3. Матвек против float-эталона** (`tools/check_matvec.py`):

| | значение |
|---|---|
| float-эталон | 4.783069 |
| Q16.16 | 4.771 |
| относительная разница | 0.25% |

Расхождение — не ошибка, а неизбежное квантование масштаба в 16 бит:
0.0038855 хранится как 254/65536 = 0.0038757. Это 0.25%. Бюджет в CI —
1%, потому что int8-квантование само по себе даёт ~0.4%.

## Что важно в дизайне

**Формат разбирается ровно в одном месте.** Первая версия проверки
проходила файл второй раз, вручную, и перепутала позицию gains `g2`
(они идут до `f1`, а не после `f2`). Получился ложный MISMATCH на
верном загрузчике. Теперь загрузчик считает CRC во время разбора, а
проверка только пересчитывает её из хранилища — знание формата живёт в
одной функции.

Это третий случай той же ошибки в проекте (детекция платформы — дважды,
формат файла — один раз). Правило, которое из этого следует: **любое
знание, продублированное дважды, рано или поздно разойдётся**.

**Веса живут в пуле, а не в арене.** `sk_pool` не отдаёт указателей, так
что один и тот же код работает и на EMS в 640 КБ, и на плоском буфере
хоста, и даёт одинаковый результат.
