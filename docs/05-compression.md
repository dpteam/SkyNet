# Сжатие: измеренная кривая и почему она не такая, как ожидалось

Статус: M3. Измерено на реальных весах, 35 вопросов, все конфигурации
загружаются и работают.

## Задача

`PROMPT.md` строка 20 требует «динамически размещаться на любом кол-ве
ОЗУ». В `docs/20-ideas.md` (И1) был предложен прогрессивный формат:
любой префикс файла весов — рабочая, но более грубая модель.

Прежде чем строить формат, надо было ответить на один вопрос: **что
именно теряется при сжатии и как быстро**. Ответ оказался неожиданным.

## Измеренная таблица

```
config           KB       accuracy  sample answer
8-bit full       373      100.0%    Lima.
8-bit hid=224    348       45.7%    It is Lima.
8-bit hid=192    324       20.0%    It is Limernie.
8-bit 3 layers   285        5.7%    The capital is Deucala.
4-bit full       205       51.4%    It is Lima.
4-bit hid=224    192       22.9%    It is Lima.
4-bit hid=192    180        5.7%    Italiana.
4-bit 3 layers   159        0.0%    It is Didgo.
```

Три способа сжать, все измерены:

| Способ | Что делает | Результат |
|---|---|---|
| меньше слоёв | отбросить блоки трансформера | **обрыв**: 3 слоя — 5.7%, 4 — 100% |
| уже FFN | отбросить нейроны `f1`/`f2` | **обрыв**: 224 — 45.7%, 256 — 100% |
| 4-битные веса | упаковать по два в байт | **плавно**: 205 КБ, 51.4% |

## Главный вывод: модель не деградирует

Два из трёх способов — не кривая, а обрыв. Отбросив **одну восьмую**
ширины FFN, вы теряете **больше половины** точности. Отбросив один слой
из четырёх — 94%.

Это значит, что «прогрессивный формат» в наивном виде (усечение) **не
работает** для этой модели. Не «работает хуже», а не работает: между
рабочей и нерабочей конфигурацией нет промежуточных.

Причина понятна: сеть обучена целиком, и каждый блок вносит вклад,
который нельзя вынуть. Это не свойство формата, это свойство обученной
модели — как нельзя вынуть из пианино половину струн и получить «тише,
но ту же мелодию».

## Единственное, что деградирует плавно

4-битные веса: 205 КБ при 51.4% точности. Половина размера за половину
качества — честный обмен, а не обрыв.

Что сделано, чтобы он был не хуже:
- таблица расширения нибблов строится один раз, горячий цикл платит
  индексацией, а не делением;
- коэффициент 127/7 компенсирует то, что масштаб строки выведен из
  8-битного диапазона: без него веса выходят в 18 раз меньше и модель
  выдаёт шум;
- эмбеддинг остаётся 8-битным. Он же выходная проекция (weight tying),
  поэтому квантование бьёт и по входу, и по распределению ответов.
  Это 9 КБ и, по замеру, 42.9% → 51.4%.

CRC считается по значениям **как они будут прочитаны**, а не по сырым
байтам файла: после упаковки в нибблы сырые байты не совпадут никогда.

## Что это значит для архитектуры

Отрицательный результат, который экономит месяцы:

1. **Не строить прогрессивный формат на усечении.** Измерено, не сработает.
2. **Меньшая модель требует обучения, а не обрезки.** Значит M4 (тренер) —
   не «следующая веха после», а предусловие для любого сжатия.
3. **MoE без обучения бесполезен.** Включение подмножества экспертов —
   это ровно то же усечение, а оно даёт обрыв. MoE имеет смысл только с
   обученным роутером, то есть после M4.
4. **4-битные веса — рабочий запасной путь.** Если памяти мало, а тренера
   нет, это единственный честный вариант: 205 КБ и 51%.

## Что осталось неизмеренным

- 4-битные веса **с обучением под квантование** (QAT) — обычно
  возвращает почти всю точность. Требует M4.
- 6-битные веса — между 4 и 8, но нестандартны и вряд ли дадут лучше
  4-бит на КБ.
- Смешанная точность по таблицам: эмбеддинг уже 8-битный, возможно и
  attention стоит держать 8-битным, а FFN — 4-битным. Не измерено.

## Как воспроизвести

```bash
python tools/compression_curve.py refs/Tiny-2.1-main/dos/TINY.BIN tests/expected.txt
```

Каждая строка — реальная конфигурация, которую программа умеет грузить
через `--layers`, `--hid`, `--bits`. Ничего не оценено на глаз.
